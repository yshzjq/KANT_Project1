| 모델 | 평균 로딩(n=18) | 평균 입력 처리(n=18) | 평균 토큰 생성 시간(n=18) | 평균 생성 속도(n=18) |
|---|---:|---:|---:|---:|
| Qwen3 4B | 0.1535초 | 0.0522초 | 0.2142초 | 104.42 tokens/s |
| Gemma 3 4B | 0.0027초 | 1.7046초 | 0.3384초 | 95.59 tokens/s |
| EXAONE 3.5 7.8B | 2.5240초 | 0.1292초 | 0.2598초 | 71.51 tokens/s |

| Llama 3.1 8B | 3.1564초 | 0.1489초 | 0.4468초 | 68.61 tokens/s |
| Gemma 3 12B | 5.8177초 | 0.4587초 | 0.9335초 | 18.56 tokens/s |

로딩=`load_duration/1e9`, 입력 처리=`prompt_eval_duration/1e9`, 생성 시간=`eval_duration/1e9`입니다. 생성 속도는 각 응답의 `eval_count/(eval_duration/1e9)`를 계산한 뒤 산술평균했습니다. 이번 108개 기록에는 필요한 통계가 있고 eval_duration이 모두 양수였습니다. 미측정 값을 0으로 채우지 않았습니다.

Phi는 tokens/s가 높아도 반복 로딩과 검색 품질 문제 때문에 선정하지 않았습니다. Gemma 4B는 로딩이 짧지만 입력 처리 평균이 1.7046초였으므로 그 지연을 반복 로딩 탓으로 돌리지 않습니다. 세부 시간의 합은 통신·서버 내부 부대 비용 등으로 호출 전체 시간과 정확히 같지 않을 수 있습니다.

## 6. PC 적합성과 최종 판단

### 메모리·적재 상태의 해석

모든 후보가 키워드 호출 18회를 성공했으므로 **이번 PC에서 해당 실행 자체는 가능**했습니다. Gemma 12B가 실행 불가능하다고 판단하지 않습니다.

원본 보고서의 VRAM과 CPU/GPU 적재 상태는 **질문 직후 고정된 최종 생성 모델**의 관측값입니다. 다른 키워드 후보의 VRAM으로 옮겨 적을 수 없습니다.

- Qwen을 키워드에도 쓴 실행에서는 동일 태그의 질문 직후 VRAM **3,693.93 MiB(약 3.61 GiB)**, `100% GPU`, 실제 `context_length=8192`가 기록되어 있습니다. 키워드 호출 직후의 별도 측정값이나 최대 VRAM은 아닙니다.
- 다른 키워드 후보의 실행 중 VRAM·CPU/GPU 분할 비율·최대 메모리 사용량은 **검토 필요**입니다.
- Qwen은 두 단계에서 같은 태그를 사용하고, 이후 키워드 호출의 로딩도 매우 짧았습니다. 이 조건은 현재 프로그램에서 유리한 실행 효율을 보여 줍니다.
- 다른 후보들의 반복 로딩은 기록에서 확인됩니다. 정확한 원인이 VRAM 부족인지, 최대 적재 모델 수 등의 서버 설정인지는 기록만으로 확정할 수 없습니다.
- Ollama는 사용 가능한 메모리와 설정에 따라 여러 모델을 유지하거나 기존 모델을 내리고 새 모델을 적재할 수 있습니다. 이 설명은 반복 로딩의 가능한 원인을 이해하기 위한 참고이며, 이번 실험의 원인을 확정하는 자료는 아닙니다. [Ollama 공식 FAQ](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)
